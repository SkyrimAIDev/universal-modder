# Mod Organizer 2, exactly

Every format below was read off real instances (MO2 2.5.2, 400–4,100 mods). `um mo2` implements all of it;
this is for when something has to be parsed or written directly.

## The virtual file system

MO2 does not install into the game. At launch it hooks the process and composites, in priority order:
the game folder, then every enabled mod's folder, then `overwrite/`. Only processes MO2 started see that
tree. Consequences worth internalising:

- A tool run outside MO2 sees the bare game. It will read the wrong inputs and write to the wrong place.
- A file "in Data" exists in no single place on disk. To find the real one, ask which mod wins
  (`um mo2 conflicts --file ...`).
- `overwrite/` is where anything written to Data at runtime lands. It sits above every mod, so leftovers
  there silently beat the mods that should be winning.

## Instance layout

Two kinds. **Portable**: `ModOrganizer.exe` and `ModOrganizer.ini` in the instance folder, data beside
them. **Managed**: only `%LOCALAPPDATA%\ModOrganizer\<instance name>\ModOrganizer.ini`, with the data at
the `base_directory` named inside it — so the ini's own folder is *not* where the mods are.

```
<instance or base_directory>/
  mods/<mod name>/            one folder per mod, its files laid out as they go into Data
  mods/<mod name>/meta.ini    what MO2 knows about it (below)
  profiles/<profile>/         modlist.txt, plugins.txt, loadorder.txt, the game INIs, saves/
  downloads/                  the archives; frequently shared with other instances
  overwrite/                  runtime output, highest priority, owned by nobody
  Stock Game/                 (Wabbajack lists) the game copied in, so a store update cannot change it
```

## ModOrganizer.ini

Qt writes strings it round-trips as `@ByteArray(...)` with **doubled backslashes**; unwrap both before use.
Paths appear in forward- and backslash forms in the same file.

| Key | Meaning |
|---|---|
| `gameName` | MO2's display name ("Skyrim Special Edition", "Skyrim VR") |
| `gamePath` | what actually launches — often `<instance>/Stock Game`, not the store install |
| `base_directory` | managed instances: where `mods/`, `profiles/`, `downloads/` really are |
| `selected_profile` | the profile in use |
| `mod_directory`, `profiles_directory`, `download_directory`, `overwrite_directory` | overrides; may contain `%BASE_DIR%` |
| `version` | the MO2 version that wrote the file |
| `N\title=`, `N\binary=`, `N\workingDirectory=` | `[customExecutables]`: the tools MO2 can launch |

Do not use `configparser` on it — it holds keys like `1\title=` and bare `%` that configparser rejects.
Read it line by line (`um.mo2.ini_values`).

## profiles/\<profile\>/modlist.txt — mod priority

**Written highest-priority-first, the reverse of MO2's left pane.** The top line wins conflicts; the bottom
is the base of the stack. Getting this backwards inverts every answer about which mod wins.

```
# This file was automatically generated by Mod Organizer.
-DO NOT DISABLE - FINAL OVERWRITES_separator      <- top of file = highest priority
+ENB Local Override (ALWAYS KEEP ON)
-Some Mod I Turned Off
*DLC: Dawnguard                                   <- bottom = lowest
```

| Prefix | Meaning |
|---|---|
| `+` | enabled |
| `-` | disabled |
| `*` | an unmanaged base-game entry (DLC/ESM placeholders); no folder of its own |
| `<name>_separator` | a UI divider, not a mod — **but MO2 does create `mods/<name>_separator/`** |

So a separator counts as present on disk, while a `*` entry never is. Mixing those up makes every separator
look like an orphan or every DLC look like a missing mod.

## profiles/\<profile\>/plugins.txt and loadorder.txt — plugin load order

`plugins.txt` carries the enabled flag, where `*` means **enabled** — a different meaning from `modlist.txt`'s
`*`. `loadorder.txt` carries the order. Where both exist, take the order from `loadorder.txt` and only the
enabled set from `plugins.txt`. `lockedorder.txt` pins specific plugins, `plugingroups.txt` holds LOOT-style
grouping. MO2 leaves timestamped backups (`plugins.txt.2026_07_01_14_59_24`) next to them — useful for
answering "what changed", and not to be parsed as current state.

Also per-profile: `skyrim.ini`, `skyrimprefs.ini`, `skyrimcustom.ini`, `initweaks.ini`, `archives.txt`, and
`saves/` when the profile keeps its own. A profile is therefore a complete, cheap, reversible branch of a
setup — the right unit to experiment in and the right thing to `um backup`.

## mods/\<mod\>/meta.ini

MO2's record of where a mod came from. It also pastes the entire Nexus description in, so these run to tens
of KB — read the keys you need and stop, don't load the file to parse it.

```ini
[General]
gameName=SkyrimSE                 ; MO2's internal name - a third spelling, not the ini's, not Nexus'
modid=31826                       ; the Nexus mod id; 0 or absent = not from Nexus
version=1.0.0.0                   ; padded to x.y.z.w, so 1.1 and 1.1.0.0 are one release
newestVersion=1.0.0.0             ; what MO2 last saw upstream
installationFile=Name-31826-1-0-1579138592.7z   ; <name>-<mod id>-<version with dashes>-<unix stamp>
repository=Nexus
ignoredVersion=                   ; a version the user chose to skip; don't report it as an update
```

A mod with no `meta.ini`, or `modid=0`, was hand-made or built by Wabbajack. Nothing can version-check it.

## Launching things

```
ModOrganizer.exe -p "<profile>" "moshortcut://:<executable title>"
```

The title must be one of the instance's `[customExecutables]` (`um mo2 tools` lists them; MO2's
Tools ▸ Executables adds them). MO2 must not already be running. `um mo2 run` builds this command.

## Reading it from code

`um/mo2.py`: `resolve()` (portable/managed → every real folder), `mod_order()` (priority-corrected),
`plugins()`, `installed_mods()`, `winner()` for one path, `mod_conflicts()` for one mod, `check()`,
`tools()`, `run()`. `um nexus` uses the same primitives, so update-checking and conflict work agree.
